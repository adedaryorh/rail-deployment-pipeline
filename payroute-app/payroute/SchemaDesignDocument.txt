1. Why I chose this structure over alternatives
The core decision was separating transactions from ledger_entries rather than storing balance changes inline on the transaction row. The simpler alternative is a single transactions table with debit_account, credit_account, and amount — fewer joins, easier at first glance. I rejected it because it collapses the audit trail. With a dedicated ledger_entries table, every balance movement is its own addressable record. You can reconstruct any account's full history by summing ledger entries alone, without touching transactions at all. That matters when you're debugging a discrepancy at 2am.
I added a transaction_status_history table rather than just a status_updated_at timestamp on the transaction. The timestamp approach loses everything in between — if a transaction goes initiated → processing → failed, you only see failed and when. The history table gives the full sequence with reasons, which is what you need for dispute resolution and compliance.
For monetary amounts I used NUMERIC(20, 8) on every balance and amount column. Float is wrong for money — it cannot represent 0.10 exactly in binary, so repeated arithmetic produces rounding drift. NUMERIC is exact arbitrary-precision decimal. I used TEXT for currency codes rather than a PostgreSQL ENUM specifically so adding new currencies never requires a schema migration — just new data rows.
2. How I ensure no money is created or destroyed
Three layers work together.
Application layer — every payment creates ledger entries in pairs inside a single database transaction. At initiation, the sender is debited and platform holding is credited by the same amount. At settlement, platform holding is debited and the recipient is credited. At failure, platform holding is debited and the sender is credited back. Both sides always match.
Database layer — the accounts table has CHECK (balance >= 0). Even if application logic has a bug, the database rejects any update that takes a balance negative. It is a last line of defence that should never trigger, but it is there.
Concurrency layer — before any debit, the sender account row is locked with SELECT FOR UPDATE inside a transaction. Two concurrent requests against the same account are serialised at the lock. The second request reads the already-debited balance after the first commits and fails the balance check. Without this, both requests could read a sufficient balance before either writes and both debit — silently creating an overdraft.
3. How I would handle adding a new currency pair in production
No schema changes are required. The accounts table uses TEXT for currency and NUMERIC for balance, so it already supports any currency. Adding a new pair is purely a data change — insert platform holding account rows for the new currency, subscribe to the live rate feed for the new symbol, and create destination accounts for clients who want to receive in that currency. No DDL, no deployment, no downtime.
4. One thing I would do differently with more time
I would add a continuous ledger reconciliation job — a scheduled query that sums all ledger entries per account and compares the result against accounts.balance. Any discrepancy triggers an immediate on-call alert. Right now the double-entry constraint is enforced by convention in application code. If a bug ever updates a balance without writing a ledger entry, it goes undetected until a manual audit. Making ledger integrity a runtime observable rather than a design assumption is the difference between catching a problem in five minutes and catching it in five days.
